# MG400 Research Notes

Date: 2026-05-07

This note summarizes web research on the Dobot MG400, focused on remote control, motion behavior, smooth execution, fault/state handling, and implications for our ARC robot runtime.

## Executive summary

- MG400 is a 4-axis desktop collaborative robot with 440 mm reach, rated payload 500 g, max payload 750 g, repeatability ±0.05 mm, and TCP/IP + Modbus TCP communication.
- Dobot’s official material distinguishes:
  - `29999` for Dashboard or settings/status commands
  - `30003` for motion commands
  - `30004/30005/30006` for feedback
- Dobot’s own programming docs show native motion primitives beyond `MovL` and `RelMovL`, including `MovJ`, `Jump`, `Arc`, and `Circle`.
- Smooth motion is not just “more waypoints”. Native `Arc`/`Circle`, the motion port, and blending options such as `CP` matter.
- `Sync()` is useful, but using it after every micro-segment destroys continuity and creates stop-and-go motion.
- Our current ARC runtime behavior matches the observed symptom: it is approximating circles by discrete waypoint-to-waypoint `MovL` moves and waiting for each step to finish.

## 1. What MG400 is

From Dobot’s product page:
- 4 axes
- 440 mm working radius
- rated payload 500 g, maximum payload 750 g
- repeatability ±0.05 mm
- max joint speed 300 deg/s on J1-J4
- communication: TCP/IP and Modbus TCP
- all-in-one desktop design, base 190 mm x 190 mm

The product page also says MG400 supports drag-to-teach, Lua programming, and graphical programming. Dobot additionally advertises vibration suppression, claiming improved multi-joint motion stability and reduced residual vibration.

## 2. Networking and controller surfaces

Official FAQ and Dobot protocol material indicate:
- `LAN1` default IP: `192.168.1.6`
- `LAN2` default IP: `192.168.2.6`
- port `502` is reserved for Modbus
- port `8172` is used by the Lua debugger

The TCP/IP protocol guide for the 4-axis controller states:
- `29999` is the Dashboard port for setting-related commands and status
- `30003` is the motion command port
- `30004` is real-time feedback at 8 ms
- `30005` is feedback at 200 ms
- `30006` is configurable feedback, default 50 ms

The official Python repo for MG400/M1 Pro mirrors that split in code examples:
- dashboard object on `29999`
- motion object on `30003`
- feedback object on `30004`

## 3. Robot modes and enable model

The Dobot TCP/IP guide describes `RobotMode()` values including:
- init
- brake open
- power-off
- disabled
- enabled
- backdrive or drag mode
- running
- recording
- error
- pause
- jog

The quickstart guide explains:
- the robot must be enabled before motion
- on first enable, payload information matters
- payload and center-of-gravity settings affect collision behavior
- before enable, J2 and J3 are mechanically locked while J1 and J4 can rotate freely

Implication for us:
- payload should not be treated as optional configuration fluff
- bad payload settings can degrade collision interpretation
- state checks should gate motion more strictly than a simple “connected” check

## 4. Motion primitives Dobot exposes

The MG400 quickstart guide lists these move types in Dobot Studio:
- `MovJ`: joint-space move, fastest and most efficient
- `MovL`: linear move
- `Jump`: built-in up-and-down transfer routine
- `JointMovJ`: move to joint position
- `RelMovJ`: relative joint-style move
- `RelMovL`: relative linear move
- `Arc`: partial circular trajectory
- `Circle`: full circular trajectory

This matters because our current ARC runtime only uses:
- `MovL(...)`
- `RelMovL(...)`

That is a strict subset of what the controller appears to support.

## 5. What “smooth” means on MG400

From Dobot’s examples and software notes, smoothness depends on several factors:

### 5.1 Motion primitive choice

- `MovJ` is fastest for repositioning, but not path-faithful.
- `MovL` preserves a straight path, good for insertions and process moves.
- `Arc` and `Circle` are native curved-path primitives, and should be preferred over polygon approximation when the controller and remote interface support them.

### 5.2 Motion channel choice

Official Dobot materials separate Dashboard from motion.

Inference from the sources:
- for best remote motion behavior, commands should be issued through the motion channel on `30003`, not treated as generic Dashboard traffic on `29999`
- even if some motion text commands can be accepted elsewhere, the officially modeled path is still “Dashboard on 29999, motion on 30003”

### 5.3 Blending and motion options

The quickstart guide’s Lua examples use options such as:
- `CP`
- `SpeedJ`
- `AccJ`
- `SpeedL`
- `AccL`

Example patterns shown by Dobot:
- `MovJ(P3, {CP=1, SpeedJ=50, AccJ=20})`
- `RelMovL({0, 0, -10, 0}, {CP=0, SpeedL=20, AccL=20})`
- `RelMovL(Offset, Option)` with `Option={CP=1, SpeedL=50, AccL=20}`

Inference:
- `CP` is part of Dobot’s path continuity or blending model
- running without controller-supported blending is likely to feel more segmented

### 5.4 Sync placement

Dobot’s quickstart repeatedly shows `Sync()` before IO-dependent logic, not after every tiny path segment by default.

The same guide says “Without the Stop at this point command, the program will not work” for certain IO workflows and explicitly points to Sync usage. The Python repo also says arrival can be judged via `Sync()` or by comparing target and actual Cartesian coordinates.

Inference:
- `Sync()` is a coordination primitive
- using it after every micro-move is safe but sacrifices continuity
- if you call `Sync()` after every segment in a pseudo-circle, the robot will look like it is stepping point to point

### 5.5 Firmware and software level effects

Dobot release notes mention:
- DobotStudio Pro v2.7.1 added “jitter suppression”
- DobotStudio Pro v2.5.0 exposed advanced switches such as `TrueMotion`, `Dynamics Optimal`, and `Compensation`
- Four-axis controller 1.7.0.2 fixed a `sync` issue where arrival could return immediately after script pause

Implication:
- some smoothness and correctness problems may be firmware/software-version sensitive
- motion semantics around `Sync()` changed enough that controller version matters

## 6. Why our current circle looks bad

Based on the current ARC runtime and Dobot documentation, the likely causes are:

1. We are approximating a circle with waypoint-to-waypoint linear moves.
2. Each waypoint is executed as a separate monitored move.
3. We wait for each move to complete before sending the next.
4. We currently do not use native `Arc` or `Circle`.
5. We currently do not expose or tune path options like `CP`, `SpeedL`, `AccL`.
6. We likely are not using the dedicated motion channel design the way Dobot’s own examples do.

Net effect:
- the robot draws a polygon, not a true circle
- more segments improve shape fidelity
- more segments also increase stop-start overhead if each segment is executed serially with strict arrival waiting

That explains the observed behavior:
- `12` segments looks visibly faceted
- `72` segments looks more circular but still slow and stepped

## 7. What the official examples suggest we should do instead

### 7.1 For true circular motion

Best path:
- use native `Arc` or `Circle` if the TCP/IP 4-axis interface exposes them for remote use

Fallback:
- if native circle is unavailable, support controller-side path files or script-side circle logic rather than host-side point stepping

Worst fallback:
- polygon approximation with dense `MovL` waypoints

### 7.2 For process moves that must remain linear

Use:
- `MovL` or `RelMovL`

But:
- allow speed, acceleration, and continuity options
- avoid unnecessary full-arrival waits between adjacent path elements if the process tolerates blending

### 7.3 For repositioning moves

Use:
- `MovJ` or `RelMovJ`

Because:
- Dobot explicitly describes `MovJ` as fastest and most efficient

### 7.4 For IO-coupled actions

Use:
- motion
- then `Sync()`
- then IO or branching logic

This matches Dobot’s examples better than inserting `Sync()` after every geometric substep.

## 8. Implications for our ARC runtime

Our current Python runtime is intentionally safety-heavy:
- it monitors motion until completion or fault
- it classifies runtime faults
- it stores incidents

That is good for safety, but it currently couples “high-integrity completion detection” with “path segmentation”. For smooth path execution, those must be separated.

Recommended architecture:

### Layer A: command submission

- dedicated motion client on `30003`
- dedicated dashboard client on `29999`
- dedicated feedback client on `30004` or `30005`

### Layer B: motion primitives

- `movj`
- `movl`
- `relmovj`
- `relmovl`
- `arc`
- `circle`
- `jump`

### Layer C: path options

- `speed_j`
- `acc_j`
- `speed_l`
- `acc_l`
- `cp`
- optional firmware-dependent smoothing flags if accessible

### Layer D: monitored execution

- submit motion
- track state and feedback
- detect:
  - started moving
  - still moving
  - finished
  - faulted
  - paused
- only force a hard wait when the task semantics require it

### Layer E: task runner

- sequence multiple moves without making the LLM manually shepherd each microscopic step
- keep incident state separate from geometric path construction

## 9. Concrete changes I would recommend next

### Priority 1

- Stop using a single generic dashboard path for all motion.
- Split connections by official role:
  - `29999` dashboard
  - `30003` motion
  - `30004/30005` feedback

### Priority 2

- Add native wrappers for:
  - `MovJ`
  - `RelMovJ`
  - `Arc`
  - `Circle`
  - possibly `Jump`

### Priority 3

- Extend ARC path tooling to accept motion options:
  - `speed`
  - `acceleration`
  - `cp`
  - maybe `mode: precise | blended`

### Priority 4

- Change circle semantics.

Today our implementation effectively treats current pose as the center and generates the first point on the perimeter. That is unintuitive.

Better options:
- `circle(center=..., radius=...)`
- or `circle_from_current(radius=..., direction=...)` where current pose is explicitly the start point on the circumference

### Priority 5

- Reserve `Sync()` for:
  - IO synchronization
  - step boundaries that actually matter
  - task completion checks

Not for:
- every tiny segment in a geometric approximation

## 10. High-confidence conclusions for our system

- The poor circle quality is not just an LLM issue.
- It is primarily a motion-execution design issue.
- The current implementation is safe-ish but geometrically crude.
- If we want motion that looks and feels “robot-native”, we need native motion primitives and controller-style queueing or blending.
- If we keep host-side waypoint stepping with full completion waits, circles will continue to look stepped no matter how clever the prompt is.

## 11. Open questions worth checking in the next implementation pass

- Does the 2024 4-axis TCP/IP guide expose `Arc` and `Circle` remotely on `30003` exactly as the local scripting environment does?
- Which parameters are accepted remotely for `CP`, `SpeedL`, `AccL`, `SpeedJ`, and `AccJ` on MG400?
- Does the controller allow queue-friendly motion submission while a previous move is still in progress?
- Can feedback data expose a reliable “motion active / queue empty / paused / faulted” distinction for our daemon?
- Are `TrueMotion`, `Dynamics Optimal`, or `Compensation` configurable remotely, or only in DobotStudio Pro?
