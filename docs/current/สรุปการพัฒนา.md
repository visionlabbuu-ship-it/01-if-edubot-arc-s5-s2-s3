## ภาพรวม

เราได้วิเคราะห์และวางแผนการพัฒนาระบบ ARC Robot เพื่อให้รองรับ browser interface และ visualization ของแขนกล โดยเน้นประสิทธิภาพและความปลอดภัย

## สิ่งที่ค้นพบ

### โครงสร้างระบบปัจจุบัน (4 ชั้น)

```
Browser UI (web/)                 ← หน้าบ้าน
    ↕ HTTP + SSE
arc-bridge.mjs                    ← ตัวต่อสาย (OpenAI-compatible)
    ↕ spawn arc CLI
ARC CLI (external/...)            ← สมอง (ยืมจาก Claude Code)
    ↕ spawn python
Python runtime (*.py)             ← ของจริง (IP ของคุณ)
```

### จุดแข็ง

- แต่ละชั้นคุยกันผ่าน process boundary (ปลอดภัย แยกได้)
- Python runtime เป็นอิสระสมบูรณ์ (CLI ที่ทำงานได้เอง)
- มี bridge และ web UI พื้นฐานอยู่แล้ว

### จุดที่ต้องปรับปรุง

1. **ช้า** — ทุกคำสั่งต้อง spawn Python ใหม่ (import numpy + เชื่อมต่อ hardware ซ้ำ)
2. **ไม่มี state** — แต่ละคำสั่งเริ่มจากศูนย์
3. **ข้อมูลไม่มีโครงสร้าง** — output เป็น JSON string ใน stdout วาดรูปไม่ได้

### 🔧 โค้ดที่สร้าง/แก้ไข

#### 1. Python Service (ใหม่)

**ไฟล์:** `arc_service.py`

**หน้าที่:**
- เปิดเป็น HTTP server ค้างไว้ (FastAPI)
- เชื่อมต่อกล้อง + แขนกลตอน startup ครั้งเดียว
- ไม่ต้อง import numpy ซ้ำทุกคำสั่ง
- มี lock กันการ move พร้อมกัน (ปลอดภัย)

**Endpoints:**
- `GET /health` — เช็คว่า service มีชีวิต
- `POST /scan` — สแกน workspace หาวัตถุ
- `GET /state` — อ่านตำแหน่งแขนทั้งหมด
- `POST /move` — สั่งเคลื่อนที่
- `POST /stop` — หยุดฉุกเฉิน
- `POST /recover` — clear error
- `POST /grip` — เปิด/ปิด suction
- `GET /list_robots` — list แขนทั้งหมด

**ความปลอดภัย:**
- ฟัง `127.0.0.1` เท่านั้น (ไม่เปิดให้ network อื่น)
- Guardrails จาก Python ยังทำงานครบ
- มี `asyncio.Lock` ต่อแขน กัน race condition

#### 2. TypeScript Integration (แก้ไข)

**ไฟล์:** `external/Agent-Robotic-Cluster/src/tools/RobotControl/shared.ts`

**การเปลี่ยนแปลง:**

1. เพิ่ม field ใหม่ใน schema (optional):
   - `scan_result` — ข้อมูลสแกนแบบมีโครงสร้าง
   - `robot_state` — สถานะแขนแบบมีโครงสร้าง

2. แตก field จาก parsed JSON:
   ```typescript
   if (toolName === 'scan') {
     return { ...baseResult, scan_result: parsed }
   }
   ```

3. เพิ่ม service mode:
   - อ่าน env `ARC_RUNTIME_MODE` (subprocess | service)
   - ถ้า service: แปลง args เป็น HTTP call แทน spawn
   - ถ้าคำสั่งไม่รู้จัก: fallback ไป subprocess อัตโนมัติ

**รองรับคำสั่ง:**
- scan, state, move, stop, recover, grip, list_robots

## ประโยชน์ที่ได้

### ประสิทธิภาพ

- **Latency ดีขึ้นมาก** — ไม่ต้อง cold start Python + import numpy ทุกครั้ง
- **State ต่อเนื่อง** — กล้อง/แขน connect ครั้งเดียว ไม่ต้อง re-init

### ความปลอดภัย

- **Guardrails ยังทำงานครบ** — อยู่ใน Python ไม่ได้ bypass
- **Concurrency safe** — มี lock กัน move พร้อมกัน
- **Rollback ได้ทันที** — subprocess mode ยังใช้ได้เต็มที่

### Visualization

- **ข้อมูลมีโครงสร้าง** — `scan_result` และ `robot_state` พร้อมให้ browser วาด
- **Contract ชัด** — มี schema บอกว่า field อะไรหมายถึงอะไร
- **ปูทางให้ Phase 3** — visualization panel พร้อมทำต่อได้เลย

## สิ่งที่ต้องทดสอบ

- [ ] รันบน hardware จริง (กล้อง + แขนกล)
- [ ] ทดสอบ concurrency — ยิง move พร้อมกัน ต้องทำทีละคำสั่ง
- [ ] ทดสอบ guardrails — คำสั่งที่ผิดกฎต้องถูกบล็อก
- [ ] วัด latency จริง subprocess vs service
- [ ] ทดสอบ service restart — crash แล้ว restart ได้ไหม
- [ ] ทดสอบ fallback — คำสั่งที่ไม่รู้จักต้อง fallback ไป subprocess

## ขั้นตอนถัดไป (Phase 3)

เมื่อ Phase 1-2 ทดสอบเรียบร้อยแล้ว:

### 3.1 แก้ bridge ให้ส่งข้อมูล structured

แก้ `bridge/arc-bridge.mjs` ให้ส่ง `scan_result` และ `robot_state` ใน SSE event `bridge.tool_result`

### 3.2 สร้าง visualization component

ใน `web/src/components/robot/`:
- `WorkspaceView.tsx` — canvas 2D วาด workspace + วัตถุ + แขน
- `RobotStatePanel.tsx` — แสดง pose ของแขนแต่ละตัว

### 3.3 เชื่อมต่อ SSE event

แก้ `App.tsx` ให้ฟัง `bridge.tool_result` แล้ววาดรูปตามข้อมูลที่ได้

### 3.4 เริ่มจาก 2D ก่อน

- วาด top-view ของ workspace (ขนาดจาก contract)
- วงกลมสี = วัตถุที่ scan เจอ
- จุด + เส้น = ตำแหน่งแขน

### 3.5 อัปเป็น 3D (ถ้าต้องการ)

เพิ่ม `react-three-fiber` และวาด 3D model ของแขนจริง
